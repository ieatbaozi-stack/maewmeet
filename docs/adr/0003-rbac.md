# ADR 0003 — RBAC: policy function กลาง `can(actor, action, resource)`

- **Status**: Proposed (Architect, 2026-10-15)
- **เกี่ยวข้อง**: [PRD §3 (สเปก), D4, D7, D8, U3, U6, U8](../prd/PRD.md) · [PROCESS ข้อ 6](../../PROCESS.md) · [ADR 0002](0002-auth-pin.md) · [ADR 0006](0006-busy-visibility.md) · [ARCHITECTURE §4–§5](../design/ARCHITECTURE.md)
- **เจ้าของการ implement**: Auth & Access (`src/lib/rbac/**`) · เทสต์เมทริกซ์: TEST (`tests/rbac/**`)

## Context
PRD §3 คือสเปกสิทธิ์ฉบับสุดท้าย (6 บทบาท × 19 การกระทำ + กติกาเสริม `must_change_pin`, super admin นอกกลุ่ม, audit) · PROCESS ข้อ 6 ห้ามเช็ก role กระจายเป็น `if` ใน route ต้องมี policy กลางเดียวที่ทุก API เรียก และเทสต์เมทริกซ์ครบทุกช่อง

## Decision

### 1. รูปร่าง (pure, synchronous, ไม่แตะ DB)
```ts
// src/lib/rbac/types.ts  (pseudo-code)
type Actor =
  | { kind: 'anonymous' }
  | { kind: 'user'; id: string; isSuperAdmin: boolean; status: 'active' | 'suspended';
      mustChangePin: boolean };

type GroupCtx = { id: string; deleted: boolean;
                  actorRole: 'admin' | 'moderator' | 'member' | null };   // null = ไม่ใช่สมาชิก
type Resource =
  | { type: 'none' }
  | { type: 'group'; group: GroupCtx }
  | { type: 'member'; group: GroupCtx; targetUserId: string; targetRole: Role }
  | { type: 'invite'; group: GroupCtx; createdBy: string }
  | { type: 'directInvite'; inviteeUserId: string }
  | { type: 'appointment'; group: GroupCtx; createdBy: string }
  | { type: 'busy'; ownerId: string }
  | { type: 'ownedByUser'; ownerId: string };          // notification ฯลฯ

type Decision = { allow: true }
  | { allow: false; code: 'AUTH_REQUIRED' | 'ACCOUNT_SUSPENDED' | 'PIN_CHANGE_REQUIRED'
                        | 'FORBIDDEN' | 'NOT_FOUND' | 'ADMIN_TRANSFER_REQUIRED'; status: 401|403|404|409 };

function can(actor: Actor, action: Action, resource: Resource): Decision
function authorize(...same): void   // throw PolicyError(decision) — service layer เรียกบรรทัดแรก
```
- ข้อมูล context (role ของ actor ในกลุ่ม, ผู้สร้างนัด/โค้ด, role ของเป้าหมาย) โหลดโดย `src/lib/data/policy-context.ts` (Platform) แล้วส่งเข้า `can()` — `can()` ไม่ query เอง จึงทดสอบเป็นตารางได้ทั้งหมด
- **จุดเรียก**: ทุก service function ใน `src/lib/data/services/**` เรียก `authorize()` เป็นบรรทัดแรก (ทั้ง Route Handler และ Server Component ใช้ service เดียวกัน) · Route Handler ทุกตัวประกาศ action ของตัวเองใน route manifest (ARCHITECTURE §5) เพื่อให้เทสต์วนได้อัตโนมัติ

### 2. ลำดับการตัดสิน (ตายตัว)
1. `anonymous` → อนุญาตเฉพาะ `PUBLIC_ACTIONS` · อื่น ๆ `AUTH_REQUIRED` (401)
2. `status = suspended` → `ACCOUNT_SUSPENDED` (401) (session ถูกลบตอนระงับอยู่แล้ว — ชั้นนี้กันเผื่อ)
3. `mustChangePin` → อนุญาตเฉพาะ `self.pin.change`, `auth.logout`, `prefs.cookie.set` · อื่น ๆ `PIN_CHANGE_REQUIRED` (403) (PRD §3 กติกาเสริม, U3)
4. action ใน `SUPER_ADMIN_ONLY` → `isSuperAdmin` ไม่งั้น `FORBIDDEN` (403)
5. resource ผูกกลุ่ม: กลุ่มไม่มี/`deleted` → `NOT_FOUND` · `actorRole = null` และไม่ใช่ super admin → `NOT_FOUND` (404 — ไม่บอกว่ากลุ่มมีอยู่) · จากนั้นใช้กฎในตารางข้อ 3
6. super admin ที่**เป็นสมาชิก**ด้วย ได้สิทธิ์ = union ของ super admin กับ role ในกลุ่ม · กฎธุรกิจ D8 (ผู้ถือ role admin ต้องโอนก่อนออก/ถูกลบ) ใช้กับทุกคนรวม super admin

### 3. รายชื่อ action ครบทุกแถวของ PRD §3
สัญลักษณ์: SA = super admin · GA = group admin · MOD · MEM = member · NM = ล็อกอินแต่ไม่ใช่สมาชิก · AN = ไม่ได้ล็อกอิน · "own" = actor เป็นเจ้าของ resource

| # | แถวใน PRD §3 | action | กฎ (หลังผ่านข้อ 2.1–2.5) |
|---|---|---|---|
| 1 | สร้างกลุ่ม | `group.create` | ผู้ใช้ทุกคน (SA GA MOD MEM NM ✅ · AN ❌) |
| 2 | ลง/แก้/ลบ busy ของตัวเอง | `busy.create` · `busy.update` · `busy.delete` · `busy.list.own` | create/list: ผู้ใช้ทุกคน · update/delete: `resource.ownerId === actor.id` |
| 3 | แก้/ลบ busy ของคนอื่น | `busy.update` · `busy.delete` (ownerId ≠ actor) | ❌ ทุกคน **รวม SA** → `FORBIDDEN` |
| 4 | ดูปฏิทินกลุ่ม / busy ของสมาชิก | `group.calendar.view` (+ `group.view` รายละเอียด/รายชื่อสมาชิก) | SA (ทุกกลุ่ม) · GA MOD MEM ✅ · NM → 404 |
| 5 | ดูวันว่างร่วมของกลุ่ม | `group.availability.view` | SA GA MOD MEM ✅ · NM → 404 |
| 6 | สร้างโค้ดเชิญ / ชวนตรง | `invite.code.create` · `invite.direct.create` (+ `invite.list`) | SA GA MOD MEM ✅ · NM → 404 · `invite.list`: GA/MOD/SA เห็นทุกโค้ดในกลุ่ม, MEM เห็นเฉพาะที่ตัวเองสร้าง (กรองใน data layer ด้วย `can(…,'invite.revoke',row)`) |
| 7 | ใช้โค้ดเชิญเข้ากลุ่ม | `invite.code.redeem` | ผู้ใช้ทุกคน · ตาราง "—" ของสมาชิกเดิม = สำเร็จแบบ idempotent ไม่สร้างแถวซ้ำ (U5 AC) · AN ❌ |
| 7b | (U5 ก: รับ/ปฏิเสธคำเชิญตรง — ไม่มีแถวใน §3) | `invite.direct.respond` · `invite.direct.list.mine` | respond: `inviteeUserId === actor.id` เท่านั้น |
| 8 | เพิกถอนโค้ดเชิญ | `invite.revoke` | SA ✅ ทุกโค้ด · GA MOD ✅ ทุกโค้ดในกลุ่ม · MEM เฉพาะ `createdBy === actor.id` · NM 404 |
| 9 | สร้างนัด (D4) | `appointment.create` (+ `appointment.view`) | SA GA MOD MEM ✅ · NM 404 |
| 10 | แก้/ยกเลิกนัด (D4) | `appointment.update` · `appointment.cancel` | SA GA MOD ✅ · MEM เฉพาะ `createdBy === actor.id` · NM 404 |
| 11 | RSVP นัดในกลุ่ม | `appointment.rsvp` | ต้อง `actorRole !== null` (**SA ที่ไม่ได้เป็นสมาชิก ❌ → `FORBIDDEN`**) |
| 12 | ลบสมาชิก (D7) | `member.remove` | SA: ทุกคน · GA: ทุกคนยกเว้นตัวเอง · MOD: `targetRole === 'member'` · MEM ❌ · **เป้าหมายถือ role admin → `ADMIN_TRANSFER_REQUIRED` (409) แม้เป็น SA** (ดูคำถามถึง Lead ใน ARCHITECTURE §9) |
| 13 | แก้ชื่อกลุ่ม / ตั้งหน้าต่างวันว่าง (D9) | `group.update` | SA GA MOD ✅ · MEM ❌ |
| 14 | แต่งตั้ง/ปลด moderator | `member.setRole` (member↔moderator เท่านั้น, เป้าหมายไม่ใช่ admin) | SA GA ✅ · MOD MEM ❌ |
| 15 | โอนความเป็น admin (D8) | `group.transferAdmin` | SA GA ✅ · เป้าหมายต้องเป็นสมาชิกปัจจุบันและไม่ใช่ตัวเอง |
| 16 | ลบกลุ่ม | `group.delete` | SA GA ✅ (soft delete + audit — U6) |
| 17 | ออกจากกลุ่มเอง (D8) | `group.leave` | ต้องเป็นสมาชิก · `actorRole === 'admin'` → `ADMIN_TRANSFER_REQUIRED` · SA ที่ไม่ใช่สมาชิก = "—" → 404 |
| 18 | อนุมัติ/ปฏิเสธ reset PIN | `pinReset.list` · `pinReset.decide` | SUPER_ADMIN_ONLY |
| 19 | หน้า super admin | `admin.console.view` · `admin.user.list` · `admin.user.suspend` · `admin.user.unlock` · `admin.group.list` · `admin.audit.view` | SUPER_ADMIN_ONLY |

Action นอกตาราง §3 (จำเป็นต่อ story แต่ไม่ใช่เรื่อง role ข้ามคน):
| action | กฎ | story |
|---|---|---|
| `auth.signup` · `auth.login` · `auth.pinReset.request` · `auth.pinReset.status` | PUBLIC (ทุกคนรวม AN; ผู้ใช้ที่ล็อกอินแล้วเรียก signup/login ได้แต่ไม่จำเป็น) | U1 U2 |
| `prefs.cookie.set` | PUBLIC + อนุญาตใน `must_change_pin` (แค่ตั้ง cookie ภาษา/ธีม ไม่แตะข้อมูล) | U14 U15 |
| `auth.logout` · `self.pin.change` | ผู้ใช้ทุกคน + อนุญาตใน `must_change_pin` | U3 U13 |
| `self.read` · `self.update` · `self.session.revokeAll` · `self.delete` | ผู้ใช้ทุกคน (เฉพาะตัวเอง) · `self.delete` ถ้ายังถือ role admin กลุ่มใด → `ADMIN_TRANSFER_REQUIRED` | U1 U13 U14 U15 |
| `group.list.mine` · `appointment.list.mine` | ผู้ใช้ทุกคน (ผลกรองตาม membership) | U4 U11 |
| `notification.list.own` · `notification.markRead.own` | `ownerId === actor.id` | ADR 0007 |
| `place.search` | ผู้ใช้ทุกคน | U10 |

**ค่าคงที่**: `PUBLIC_ACTIONS`, `PIN_CHANGE_ALLOWED = ['self.pin.change','auth.logout','prefs.cookie.set']`, `SUPER_ADMIN_ONLY` อยู่ใน `src/lib/rbac/actions.ts` ไฟล์เดียว · `Action` เป็น union type จาก `as const` array
**audit**: action ที่ SA ทำต่อกลุ่ม/ผู้ใช้ที่ไม่ใช่ตัวเอง (และ `group.calendar.view`/`group.availability.view` ของ SA ที่**ไม่ใช่สมาชิก**) → service เขียน `audit_log` (PRD §3 กติกาเสริม) — `can()` คืนค่า `auditAsSuperAdmin: true` ให้ service รู้

### 4. วิธีทำเทสต์เมทริกซ์ให้ครบทุกช่องอัตโนมัติ
1. **Fixture = PRD §3 แบบตรงตัว** — `tests/rbac/matrix.fixture.ts` (TEST) เขียนแถวละ action, คอลัมน์ `SA_nonmember | SA_member | GA | MOD | MEM | NM | AN` ค่าที่เป็นไปได้ `allow | deny | na` · ช่องมีเงื่อนไข ("เฉพาะที่ตัวเองสร้าง", "เฉพาะ member", "ยกเว้นตัวเอง") แตกเป็น **scenario** ย่อย (own/other, targetRole = member/moderator/admin/self)
2. **ความครบถ้วนบังคับด้วย type + runtime**: fixture ประกาศเป็น `satisfies Record<Action, MatrixRow>` → เพิ่ม action ใหม่แล้วลืมเติม = compile ไม่ผ่าน · เทสต์ runtime เทียบชุดคีย์ fixture กับ `ACTIONS` ต้องเท่ากันพอดี
3. **ชั้น unit** (เร็ว): สร้าง test case แบบผลคูณ `ACTIONS × ACTOR_VARIANTS × SCENARIOS` แล้วเทียบ `can()` กับ fixture (`test.each`) — ไม่มีช่องไหนเขียนมือซ้ำ
4. **ชั้นสถานะพิเศษ** (คูณซ้ำทุก action): `must_change_pin` → deny ทุก action ยกเว้น 3 ตัว · `suspended` → deny ทุก action · กลุ่ม `deleted` → `NOT_FOUND` ทุก action ที่ผูกกลุ่ม
5. **ชั้น integration (HTTP)**: route manifest (`src/app/api/_lib/manifest.ts`) ผูก `method + path → action + วิธีสร้าง resource` · เทสต์ seed DB ด้วย actor ทุกแบบแล้วยิงทุก route ผ่าน handler จริง ตรวจ HTTP class (2xx / 401 / 403 / 404 / 409) ตรง fixture
6. **กันทางหลบ**: เทสต์สแกน `src/app/api/**/route.ts` ทั้งหมด → ทุกไฟล์ต้องมีอยู่ใน manifest (ยกเว้น allowlist `health`, `cron/daily` ที่ใช้ `CRON_SECRET`) · lint rule ห้าม import `src/lib/data/repos/**` จาก `src/app/**` (ต้องผ่าน services)

## Alternatives considered
| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| ไลบรารี ABAC/RBAC (CASL, Casbin) | ความสามารถเกินจำเป็น, กฎเขียนเป็น DSL ที่ type-check ยาก, เพิ่ม dependency — กฎเราไม่เกิน ~40 action เขียนเป็นตาราง TS อ่านง่ายกว่าและ exhaustive ด้วย compiler |
| ตรวจ role ใน Route Handler แต่ละตัว | ขัด PROCESS ข้อ 6 ตรง ๆ และ Server Component จะไม่ได้ตรวจ |
| ตรวจสิทธิ์ใน `proxy.ts` | เห็นแค่ URL ไม่เห็น resource (ผู้สร้างนัด, role เป้าหมาย) และ Next แนะนำไม่ให้พึ่ง proxy เป็นด่านเดียว |
| ตอบ 403 ให้คนนอกกลุ่ม | บอกเป็นนัยว่ากลุ่ม id นี้มีจริง — เลือก 404 (PRD U8 ยอมรับทั้งสองแบบ) |

## Consequences
- + จุดเดียวให้ Security reviewer ตรวจ · เทสต์สร้างจาก PRD ตรงตัว เมื่อ PRD เปลี่ยน แก้ fixture แล้ว compiler ชี้ทุกที่
- + Server Component กับ API ได้สิทธิ์เท่ากันแน่นอน
- − ทุก service ต้องโหลด context ก่อน (1 query JOIN membership) — ยอมรับได้
- − โค้ด 404 สำหรับคนนอกกลุ่มทำให้ debug ยากขึ้นเล็กน้อย (log ฝั่งเซิร์ฟเวอร์บันทึกเหตุผลจริงโดยไม่ใส่ข้อมูลลับ)

## Test requirements
- PRD §8 ข้อ 2: เมทริกซ์ผ่าน **ทุกช่องของ §3 ทั้ง 19 แถว × 6 คอลัมน์** + SA ที่เป็น/ไม่เป็นสมาชิก + `must_change_pin` + `suspended` + กลุ่มถูกลบ (หัวข้อ 4 ข้อ 1–5)
- U3: ทุก route ใน manifest ตอบ 403 `PIN_CHANGE_REQUIRED` ระหว่าง `must_change_pin` ยกเว้น 2 route ใน PRD (+ `prefs`)
- U6: ผู้ถูกลบออก → request ถัดไปต่อ `group.view`/`group.calendar.view` ได้ 404 ทันที (ไม่มี cache) · D7: MOD ลบ MOD/GA → 403 · D8: GA `group.leave` → 409 จนกว่าจะโอน · SA ลบ GA → 409, หลัง `group.transferAdmin` → สำเร็จ
- U8: NM ได้ 404 ทุก endpoint กลุ่ม (ทั้ง API และหน้า Server Component — E2E)
- audit: SA ทำ `member.remove` / `group.transferAdmin` / `group.delete` / `pinReset.decide` / `admin.user.suspend` / ดูปฏิทินกลุ่มที่ตัวเองไม่ได้อยู่ → มีแถวใน `audit_log` ทุกครั้ง
- เทสต์ "ทุก route.ts อยู่ใน manifest" และ lint "ห้าม import repos จาก app" ต้องล้มเมื่อจงใจทำผิด (มี test case ด้านลบ)
