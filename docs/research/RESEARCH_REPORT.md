# รายงานวิจัย: แมวเจอกัน (maewmeet)

> ทำเมื่อ 2026-10-15 · สำหรับ boss ตัดสินใจก่อนเริ่มเขียน requirements
> ความน่าเชื่อถือ: ข้อมูล LINE มาจากเอกสารทางการ developers.line.biz (ค้นเมื่อวันที่ทำรายงาน) ส่วนที่มาจากความรู้เดิมของ agent ติดป้าย **ต้องเช็กซ้ำ** — ราคา/โควตาเปลี่ยนบ่อย ยืนยันกับหน้าทางการก่อนผูกมัด

## 1. สรุปสั้น (คำแนะนำของผม)
1. **ทำได้ครบตามที่ boss คิดเรื่อง LINE**: ผูกบัญชีตอน login, ส่งแจ้งเตือน reset PIN / นัดใหม่เข้าแชทส่วนตัว — แต่ต้องมี **LINE Official Account** คู่กับ LINE Login และผู้ใช้ต้อง **เพิ่มบัญชีทางการเป็นเพื่อน** ก่อน ระบบถึงจะส่งหาเขาได้ (รายละเอียดข้อ 2)
2. **แนะนำให้ LINE เป็น v1.x** แต่เตรียมโครงรองรับใน v1 (ฟิลด์ `line_user_id`, ตาราง `notification_outbox`, ชั้น "ส่งแจ้งเตือน" แบบเสียบช่องทางได้) เพื่อไม่ต้องรื้อทีหลัง
3. **Stack**: Next.js + TypeScript + Drizzle + Turso + Vercel เหมือนโปรเจกต์ก่อน (ทีมคุ้นมือ ต้นทุนใกล้ 0) · ไม่ต้องใช้บริการอีเมลใน v1 เพราะ login ด้วย PIN
4. **PIN 6 หลักอ่อนโดยธรรมชาติ** (1 ล้านแบบ) ต้องชดเชยด้วย hash ที่ถูกวิธี + lockout/throttle + บังคับเปลี่ยน PIN หลัง reset เป็น 123456 (ข้อ 3)
5. **แผนที่**: ใช้ OpenStreetMap + ลิงก์เปิดแอปแผนที่ในเครื่อง ไม่ผูก Google Maps API ที่ต้องมีบัตร (ข้อ 4)
6. **งานเสี่ยงที่สุดของโปรเจกต์ไม่ใช่ UI แต่คือ "เวลา" กับ "สิทธิ์"** จึงมีบทบาท Calendar & Time และ Auth & Access แยกเป็นเจ้าของ พร้อมเกตเทสต์เฉพาะ

## 2. คำตอบเรื่อง LINE (คำถามข้อ 6 ของ boss)

### ภาพรวมว่า "ทำได้แค่ไหน"
| ความต้องการ | ทำได้ไหม | วิธี/เงื่อนไข |
|---|---|---|
| ผู้ใช้ผูกบัญชีตัวเองกับ LINE ตอน login | **ได้** | LINE Login (OAuth 2.0/OpenID Connect) ได้ `userId` ของผู้ใช้ |
| ส่งข้อความเข้าแชทส่วนตัวของผู้ใช้ | **ได้ มีเงื่อนไข** | ส่งผ่าน Messaging API (push message) ไปที่ `userId` — **ผู้ใช้ต้องเป็นเพื่อนกับ LINE Official Account ของเรา** และไม่ได้บล็อก |
| ให้ผู้ใช้เพิ่ม OA เป็นเพื่อนตอน login เลย | **ได้** | ผูก OA เข้ากับ LINE Login channel แล้วใส่พารามิเตอร์ `bot_prompt` (`normal` = ตัวเลือกบนหน้า consent, `aggressive` = ขึ้นหน้าชวนเพิ่มเพื่อนหลัง consent) — ผูกได้ 1 OA ต่อ 1 LINE Login channel และ Messaging API channel ต้องอยู่ใน provider เดียวกับ LINE Login channel |
| แจ้ง reset PIN / นัดใหม่ / เตือนก่อนนัด | **ได้** | ผ่าน push ไปที่ `userId` (ให้ระบบ outbox ส่งและ retry) |
| รับ event เช่น เพิ่มเพื่อน/เลิกเป็นเพื่อน | **ได้** | webhook ของ Messaging API ส่ง event ไปยัง URL ของเรา (ใช้ตรวจว่าผู้ใช้ยังรับข้อความได้ไหม) |
| ใช้ LINE แทนการ login ด้วย PIN ทั้งหมด | ได้ แต่ **ไม่แนะนำเป็นทางเดียว** | เก็บ PIN เป็นทางหลักตามที่ boss สั่ง ให้ LINE เป็นตัวเลือกผูกเพิ่ม (ยังไม่เปลี่ยนความต้องการเดิม) |

### เรื่องที่ต้องรู้ก่อนตัดสินใจ
1. **`userId` เป็นค่าเดียวกัน ถ้า channel อยู่ใน provider เดียวกัน** — ID ของผู้ใช้ที่ได้จาก LINE Login จึงใช้ส่ง push ผ่าน Messaging API ได้ตรงๆ ไม่ต้องเก็บคู่ ID สองชุด (ต้องสร้าง LINE Login channel และ Messaging API channel ใต้ provider เดียวกัน)
2. **ส่งหาคนที่ไม่ได้เป็นเพื่อนไม่ได้** — ถ้าผู้ใช้ไม่เพิ่มเพื่อนหรือบล็อกทีหลัง ต้องมีทางสำรอง (แจ้งเตือนในแอป + super admin เห็นสถานะ reset ในหน้า admin)
3. **โควตาข้อความ**: ข้อความแบบ push/multicast/broadcast นับตามจำนวน **ผู้รับ** (ส่ง 1 ข้อความหา 10 คน = 10) ส่วน reply ไม่นับ · ถ้าเกินโควตาฟรีรายเดือนจะได้ error 429 "monthly limit" · จำนวนข้อความฟรีขึ้นกับแผนและประเทศ (**ต้องเช็กซ้ำ**: แหล่งที่ค้นเจอให้ตัวเลขไม่ตรงกัน ตั้งแต่หลักร้อยถึง 500 ต่อเดือน ให้ boss ดูในหน้า LINE Official Account Manager ของบัญชีไทยที่จะใช้ก่อน) — ตัวอย่างขนาด: กลุ่ม 10 คน นัดใหม่ 1 ครั้ง = 10 ข้อความ → กลุ่มเพื่อนไม่กี่กลุ่มน่าจะพอ แต่ต้องออกแบบให้ **รวมการแจ้งเตือน (ไม่ส่งทุกการเปลี่ยนแปลง)** และมีตัวนับโควตาใน outbox
4. **LINE Notify เลิกให้บริการแล้ว** (ตามความรู้เดิม ปิดบริการต้นปี 2025, **ต้องเช็กซ้ำ**) ทางที่ใช้ได้คือ Messaging API เท่านั้น
5. **webhook**: ต้องตรวจลายเซ็น `X-Line-Signature` (HMAC-SHA256 ด้วย channel secret) ทุกครั้ง · ต้องเป็น HTTPS ที่เข้าถึงได้จากภายนอก (Vercel ใช้ได้) · ตอบ 200 เร็ว งานหนักทำทีหลัง
6. **อย่าส่ง PIN ผ่านแชท** — PIN ใหม่หลัง reset คือ `123456` ที่ทุกคนเดาได้ ข้อความ LINE ควรบอกเพียงว่า "คำขอ reset ได้รับอนุมัติแล้ว ให้เข้าสู่ระบบแล้วตั้ง PIN ใหม่ทันที" และต้องไม่ใช้ LINE เป็นหลักฐานยืนยันตัวตนสำหรับ reset อัตโนมัติ (ยังต้องผ่านการอนุมัติจาก super admin ตามที่ boss กำหนด) — LINE ช่วยแค่ "แจ้งผล"
7. **ผู้ใช้ที่ไม่ใช้ LINE**: ต้องใช้แอปได้ปกติทุกอย่าง LINE เป็นส่วนเสริม
8. ทางเลือกเสริมภายหลัง: **LIFF** เปิดเว็บแอปในหน้าต่างใน LINE (ล็อกอินแทบไม่มีแรงเสียดทาน) — ยังไม่แนะนำสำหรับรอบแรก (ต้องเช็กซ้ำรายละเอียดตอนทำ R7)

### ลำดับงานที่เสนอ
- v1: `line_user_id` nullable + `notification_outbox` + ชั้นส่งแจ้งเตือนแบบเสียบช่องทาง (ช่องทางเดียวคือ "ในแอป")
- v1.x (R7): boss สร้าง provider + LINE Login channel + Messaging API channel + OA → ทีมทำผูกบัญชี/`bot_prompt`/webhook/ส่งแจ้งเตือน 3 แบบ (reset ได้รับอนุมัติ, นัดใหม่, เตือนก่อนนัด)
- **สิ่งที่ boss ต้องทำเอง**: สมัคร LINE Developers + สร้างช่อง + ได้ channel secret/token (เก็บใน env) · ตั้งชื่อ/รูปบัญชีทางการ · ดูแผนข้อความ

## 3. Auth ด้วย PIN 6 หลัก (ความเสี่ยงและวิธีลด)
PIN 6 หลักมีเพียง 1,000,000 แบบ ต่อให้ hash ดี ถ้าฐานข้อมูลรั่วจะแกะได้เร็วมาก ข้อกำหนดที่เสนอให้ Auth & Access ทำเป็น ADR:
- hash ด้วย argon2id (หรือ bcrypt) + ค่าลับฝั่งเซิร์ฟเวอร์ (pepper) เก็บใน env ไม่ใช่ในฐานข้อมูล เพื่อให้ฐานรั่วอย่างเดียวแกะไม่ได้
- จำกัดความถี่ลองผิดต่อ username **และ** ต่อ IP, ล็อกชั่วคราวแบบถอยหลังเพิ่มเวลา, ตอบข้อความเดียวกันไม่ว่า username ไม่มีหรือ PIN ผิด (กันไล่เดาชื่อ)
- session ยาว (เช่น 60 วัน) ผูกอุปกรณ์ ไม่ถาม PIN บ่อย · ออกจากระบบทุกเครื่องได้
- **หลัง reset เป็น `123456`**: ใครรู้ username ก็เข้าได้ระหว่างรอ จึงเสนอ (1) PIN ชั่วคราวใช้ได้เฉพาะภายในกรอบเวลา เช่น 24 ชม. และใช้ได้ครั้งเดียวเพื่อไปหน้าตั้ง PIN ใหม่, (2) บังคับเปลี่ยนก่อนทำอย่างอื่น, (3) พิจารณาผูกกับอุปกรณ์ที่กดขอ reset (โทเค็นในเบราว์เซอร์ของผู้ขอ) — ให้ Architect ตัดสินใน ADR
- reset ทุกครั้งลง audit log (ใคร อนุมัติ เมื่อไร)
- กลุ่มเพื่อนปิดไม่มีข้อมูลการเงิน ความเสี่ยงยอมรับได้ถ้าทำตามข้างต้น แต่ boss ควรรู้ว่านี่คือ trade-off เพื่อความง่าย

## 4. Stack, แผนที่, Deploy
- **ข้อกำหนดจาก boss**: ฐานข้อมูลใช้ **SQLite บน Turso** และ deploy บน **Vercel** เหมือนโปรเจกต์เดิม — ถือเป็นข้อตกลงตายตัว ไม่ต้องประเมินทางเลือกอื่นใหม่
- **Stack**: Next.js (App Router) + TypeScript · Drizzle + Turso (libSQL) · session แบบเขียนเอง/เลือกไลบรารีตาม ADR ของ Architect (PIN + username ไม่ตรงกับ flow สำเร็จรูปส่วนใหญ่ **ต้องเช็กซ้ำ** ว่า Better Auth ทำ credential แบบ PIN ได้สะดวกไหม) · Tailwind + tokens · Vitest + Playwright (มือถือ + iPad) · GitHub Actions · Vercel
- **ต้นทุน**: ประมาณ $0–5/เดือนที่ขนาดหลักสิบถึงร้อยคน (ต้องเช็กซ้ำราคา Turso/Vercel ปัจจุบัน) · **Vercel Hobby ใช้ได้เฉพาะงานไม่แสวงหากำไร** ถ้าจะเก็บเงินภายหลังต้องขึ้นแผนอื่น
- **PWA**: ทำ manifest + ไอคอนให้ติดตั้งหน้าจอหลักได้ (iOS ต้อง Share → Add to Home Screen เอง ทำแบนเนอร์สอน) ไม่ทำออฟไลน์เต็มรูปแบบใน v1
- **แผนที่/pin สถานที่**: เก็บ `place_name` + `lat/lng` (+ ลิงก์ Google Maps/Apple Maps ที่ผู้ใช้วางได้) · แสดงแผนที่ด้วย OpenStreetMap (Leaflet/MapLibre) · ค้นหาสถานที่ด้วย Nominatim ต้องทำตามนโยบายของเขา (ราว 1 req/วินาที ห้าม autocomplete ทุกตัวอักษร **ต้องเช็กซ้ำ**) → ให้พิมพ์ชื่อ + กดค้นหา หรือวางลิงก์/พิกัดแทน
- **เวลา**: ดีฟอลต์ Asia/Bangkok ไม่มี DST แต่ต้องรองรับ timezone ต่อรายการไว้ในโมเดล (เผื่อเที่ยวต่างประเทศ) · ไลบรารีวันเวลา (เช่น Temporal polyfill/date-fns-tz/Luxon) เลือกใน ADR

## 5. ตัวอย่างนิยาม "วันว่างร่วม" (ให้ Calendar & Time ใช้เป็น test case ตั้งต้น)
- กลุ่ม 3 คน หน้าต่างวัน 08:00–22:00
- A busy 10:00–12:00 · B busy ทั้งวัน · C ไม่ busy → วันนี้ **ไม่ว่างร่วม** (B ทั้งวัน) แต่ "ว่าง 2/3"
- A busy 10:00–12:00 · B busy 14:00–16:00 · C ว่าง → ช่วงว่างร่วม: 08:00–10:00, 12:00–14:00, 16:00–22:00 (แสดงเฉพาะที่ ≥ 2 ชม. = ทั้งสามช่วง)
- busy ข้ามเที่ยงคืน 31 ธ.ค. 22:00 → 1 ม.ค. 02:00 ต้องแบ่งไปคิดทั้งสองวันถูกต้อง
- busy หลายวัน 28 ก.พ.–2 มี.ค. ปีอธิกสุรทิน/ไม่ใช่

## 6. ความเป็นส่วนตัว
- ตาราง busy ของใคร มองเห็นได้เฉพาะคนในกลุ่มเดียวกันที่ผู้ใช้เป็นสมาชิก (ต้องมีเทสต์ยืนยัน) · เปิดให้ซ่อนรายละเอียด "ทำอะไร" เหลือแค่ "ไม่ว่าง"
- ข้อมูลพิกัดสถานที่นัดเป็นของกลุ่ม ไม่ใช่ตำแหน่งผู้ใช้ — ไม่เก็บตำแหน่งปัจจุบันของใคร
- ข้อมูลส่วนบุคคลที่เก็บ: username, ชื่อที่แสดง, (v1.x) LINE userId → ควรมีประกาศความเป็นส่วนตัวสั้นๆ และปุ่มลบบัญชี/ออกจากกลุ่ม (ไม่ใช่คำปรึกษากฎหมาย)
