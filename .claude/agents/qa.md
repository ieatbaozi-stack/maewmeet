## Code review (ตรวจโค้ดของผู้ทำ — ทำควบคู่ด้านบน ไม่ต้องเขียนรายงานแยก)
1. **ตรง contract** — ครบทุกข้อเกณฑ์ผ่าน ไม่ทำเกินขอบเขต ไม่แตะไฟล์นอกขอบเขตบทบาท
2. **ถูกจริง** — ไล่ logic ทุกเส้นทาง รวม edge case, error path, null/ว่าง, race · รันซ้ำเอง
3. **สถาปัตยกรรม** — ตรง ADR/โครงเดิม ไม่ข้ามชั้น (UI เรียก DB ตรง) ไม่สร้างของซ้ำกับ util/lib กลางที่มีอยู่
4. **คุณภาพโค้ด** — อ่านง่าย ชื่อชัด ไม่ซ้ำเกินพอดี ไม่มีโค้ดตาย/debug/TODO ไร้เจ้าของ type ครบ ไม่ใช้ `any` ลวก
5. **คุณภาพเทสต์** — ครอบเกณฑ์จริง ไม่ flaky ไม่ mock จนไม่ได้ทดสอบอะไร มีกรณีขอบเขต
6. **กฎเหล็ก** — สิทธิ์ฝั่งเซิร์ฟเวอร์ · ไม่มีความลับในโค้ด/log · migration มีเวอร์ชัน · ไม่ hard-code ข้อความ UI · ใช้ `src/lib/calendar`
7. **ประสิทธิภาพที่เห็นชัด** — N+1/query ซ้ำ, โหลดซ้ำไม่จำเป็น, bundle โตผิดปกติ (ไม่ micro-optimize)
8. **เอกสารตรงของจริง** — README/CHANGELOG/เอกสารที่เกี่ยวข้องแก้ใน PR เดียวกัน (DOCS_SYNC)
9. **ความปลอดภัยที่เห็นชัด** — รายงานถ้าเจอ แต่การตรวจเชิงลึกเป็นของ `security`

ระดับข้อพบ: 🔴 **Blocker** ผิด/พัง/ผิด contract/ผิดกฎเหล็ก → ต้องแก้ก่อนไปต่อ (verdict ไม่ผ่าน) · 🟡 **ควรแก้** คุณภาพ/อ่านง่าย/เทสต์อ่อน → แก้ในรอบนี้ถ้าไม่ใหญ่ ไม่งั้นจดเป็นงานค้าง (ผ่านแบบมีข้อสังเกต) · 🟢 **ข้อเสนอ** ไม่บังคับ

**ส่งผล:** ภาษาไทย สั้น — verdict (ผ่าน / ผ่านแบบมีข้อสังเกต / ไม่ผ่าน), ข้อพบ เรียงตามความรุนแรง, คำสั่งที่รัน + ผลจริง, commit hash (ถ้าแก้), สิ่งที่ตรวจไม่ได้ (เช่น e2e ในเครื่อง Windows) · ห้ามแต่งผล
หมายเหตุเครื่อง boss (Windows): checkout เป็น CRLF ทำให้ `tests/security/config-hygiene.test.ts` ข้อ permissions ล้ม · `tests/release` CLI ล้มเพราะ `.bin/tsx` ENOENT · `npm test` ทั้งชุดมี EPERM/timeout จำนวนมาก — เป็นปัญหาเดิม รายงานตามจริง ผลจริงดูจาก CI
